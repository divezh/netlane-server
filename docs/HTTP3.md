# HTTP/3: обрыв при заполнении окна QUIC

## Симптом и причина

Клиент подключается через HTTP/3, затем теряет DNS/трафик и переходит в восстановление с ошибкой:

```text
Http3Client::input:1405: ERR_CALLBACK_FAILURE (-502): (261)
```

Последнее число — код HTTP/3 `261 = 0x0105 = H3_FRAME_UNEXPECTED`.
Код QUIC `-502` сообщает об ошибке callback и сам по себе не объясняет её причину.
В данном случае удалось воспроизвести серверный дефект: поток ответа завершается FIN до получения HEADERS.
Это нарушение HTTP/3 затрагивает всё соединение, а не только один запрос.
См. [RFC 9114, порядок сообщений](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.1)
и [исходный отчёт upstream](https://github.com/TrustTunnel/TrustTunnel/issues/164).

В закреплённом endpoint v1.1.0 `StreamSink` хранит ответ при `StreamBlocked`.
Когда sink уничтожается (health check, ошибка CONNECT), заголовки теряются,
а закрытие отправляет пустой FIN. У UDP-соединения DATA также могли попасть в поток раньше HEADERS.
Недоступность админки сама по себе не вызывает этот дефект: VPN обслуживает `trusttunnel-managed`,
а синхронизацию ноды выполняет отдельная служба `trusttunnel-node`.

## Исправление

Патч `upstream/patches/0008-http3-deferred-response.patch`:

- Передаёт codec совместное владение отложенным ответом. Заголовки сохраняются после удаления sink.
- Повторяет отправку при освобождении окна, в том числе у активного UDP-туннеля без новых пакетов.
- Отправляет HEADERS перед DATA и FIN, а при необратимой ошибке сбрасывает только соответствующий поток.
- Ждёт увеличения ёмкости после отказа атомарной отправки HEADERS. Порог для небольшого DATA-кадра недостаточен и вызывал цикл повторов без ожидания.

Версия исправленного endpoint содержит `-admin-preview.5-quic.1`.
Managed API, формат состояния, квоты и политика блокировки торрентов совместимы с предыдущей сборкой.
Протокол на клиенте менять не требуется; исправление работает для Windows и macOS.

## Воспроизведение и проверки

После применения всех патчей из [upstream/README](../upstream/README.md):

```bash
cargo test --locked -p trusttunnel --test http3_backpressure
cargo fmt --all -- --check
cargo clippy --locked -- -D warnings
cargo test --locked --workspace
```

Тесты создают настоящий QUIC endpoint на loopback и задают клиенту окно соединения 128 байт.
Пакет из 64 одновременных health check или неудачных CONNECT вынуждает сервер отложить заголовки.
Проверяется, что у каждого ответа HEADERS приходят до FIN и соединение остаётся открытым.
Третий тест проверяет UDP echo при том же заполненном окне и доставку заголовков без следующего UDP-пакета.
Исходная реализация проваливает проверку порядка HEADERS/FIN; простого сохранения заголовков также недостаточно
для ответов 502 и UDP, поэтому эти случаи проверяются отдельно.

## Проверка на ноде

Сначала проверьте установленный движок:

```bash
/opt/trusttunnel/bin/trusttunnel_endpoint --version
journalctl -u trusttunnel-managed -u trusttunnel-node -n 100 --no-pager -o short-iso
```

Обновление выпущенного комплекта выполняется по [инструкции обновления](UPDATES.md).
Исправление ставится на все VPN-локации, через которые используются HTTP/3-подключения.
Перезапуск `trusttunnel-managed` прерывает действующие VPN-сессии, после чего клиенты переподключаются.

После обновления проверьте наличие `quic.1` в версии и HTTP/3 под той же нагрузкой,
при которой происходили обрывы, минимум 10–15 минут. Сохраните клиентский лог и журнал endpoint.
Прошедший локальный тест подтверждает устранение воспроизведённого дефекта;
проверка реального сетевого пути всё равно нужна для подтверждения результата на конкретной ноде.
