# Обновление панели

Сервер обновляется только из **последнего релиза** публичного репозитория [`divezh/netlane-server`](https://github.com/divezh/netlane-server/releases/latest). Токен не нужен.

Панель читает `https://api.github.com/repos/divezh/netlane-server/releases/latest`: тег `netlane-X.Y.Z` — версия, ассет `trusttunnel-dev.tar.gz` — комплект, его `digest` (SHA-256 от GitHub) — контрольная сумма, пункты списка из описания релиза — «Что нового». Черновики и pre-release не учитываются. Комплект скачивается только с `github.com/divezh/netlane-server/releases/download/`; SHA-256 сверяется до установки.

## Проверка из панели

Раздел «Сервер» → карточка «Обновление панели»: установленная версия, опубликованная, примечания выпуска. Ответ GitHub кешируется на две минуты; недоступный GitHub не ломает страницу — карточка пишет, что проверка не удалась, и предлагает SSH.

`GET /api/v1/updates` отвечает `{current, latest, available, reachable, notes, notes_url, can_apply}`.

## Установка из панели

Панель запускается без прав root (`NoNewPrivileges=true` в `trusttunnel-admin.service`), поэтому сама ничего не устанавливает и не запускает sudo. Кнопка «Обновить до X» оставляет запрос в `<каталог базы>/update-requested`. С 0.5.19 его сразу замечает `trusttunnel-update.path` (PathExists) и запускает `/usr/local/sbin/netlane-update --requested` через секунду после нажатия; `trusttunnel-update.timer` (`OnCalendar=*:0/2`) остаётся запасным. Прежний таймер с `OnUnitActiveSec` мог остаться без следующего запуска, и запрос висел на «Запрос отправлен». Дальше работает обычный обновлятор: находит запрос, скачивает комплект из последнего релиза, сверяет SHA-256, делает резервную копию, ставит программу и перезапускает службы; если они не поднялись — возвращает прежнюю версию.

Обновлятор пишет отчёт в `<каталог базы>/update-status.json`: текущий шаг, процент, подробность (мегабайты, SHA-256, имя резервной копии) и историю шагов с временем (`steps`), при ошибке — точную причину и `failed_stage`. Карточка «Обновление панели» рисует это списком шагов; отчёт об успешном обновлении остаётся на карточке 15 минут. Новый запрос стирает отчёт прошлого запуска.

Страница ждёт возврата панели и перезагружается сама; сессия после перезапуска не сохраняется, поэтому вход потребуется снова. Ход обновления виден в журнале: `journalctl -u trusttunnel-admin -u trusttunnel-update -n 100`.

`POST /api/v1/updates/apply` требует сессию администратора и CSRF-токен, пишет в журнал действий `panel.update_started` и отвечает `202`. Кнопка показывается, только когда таймер установлен; иначе карточка предлагает обновиться по SSH.

## Что нужно на сервере

`trusttunnel-update.path`, `trusttunnel-update.timer` и `trusttunnel-update.service` ставят установщик и обновлятор: обновлятор при любом запуске приводит их к нужному виду. Сервер, пришедший со старой версии, получает таймер при первом же запуске нового обновлятора — после ручного обновления достаточно один раз выполнить `sudo netlane-update --check`. Дальше обновления ставятся из панели.

## Обновление по SSH

`setup.sh` для обновления не используется. Обычно хватает `sudo netlane-update`. Если сервер не может скачать файлы с GitHub, загрузите `trusttunnel-dev.tar.gz` и `.sha256` из релиза в `/root` вручную:

```bash
cd /root
sha256sum -c trusttunnel-dev.tar.gz.sha256 && \
netlane-update --file /root/trusttunnel-dev.tar.gz --yes
```

Проверка без установки: `netlane-update --check` (код возврата 10, если доступна новая версия). Своя сборка: `NETLANE_REPO=owner/repo` задаёт другой репозиторий для `netlane-update`. Локальный стенд без systemd может указать `NETLANE_UPDATE_TIMER` на существующий файл — тогда карточка показывает кнопку, но установку всё равно делает только настоящий таймер.

## Команда обновлятора

| Аргумент | Что делает |
| --- | --- |
| без аргументов | проверяет последний релиз, спрашивает и устанавливает |
| `--check` | только проверка, код 10 при новой версии |
| `--yes` | без вопроса |
| `--requested` | обновляет только при запросе из панели (для таймера) |
| `--file F.tar.gz` | установка скачанного комплекта |
| `--set-token` | необязательный токен GitHub: поднимает лимит в 60 запросов в час |

## Выпуск версии

1. Обновить версию в CHANGELOG и закоммитить в `main`.
2. Actions → Release → Run workflow, тег `netlane-X.Y.Z`. Workflow тестирует коммит, собирает комплект с версией X.Y.Z и публикует релиз `Netlane X.Y.Z - Server` с `trusttunnel-dev.tar.gz` и `.sha256`.
3. Через пару минут после публикации серверы видят новую версию в карточке «Обновление панели».

Релиз сразу становится доступен всем серверам, поэтому публикуйте только готовые версии; для проверок используйте pre-release — его обновлятор не берёт.
