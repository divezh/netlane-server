# Установщик и восстановление незавершённой установки

Исходники: `scripts/netlane-setup.sh` → `setup.sh` в комплекте; `deploy/dev/install.sh` → `install.sh`; рядом обязательно находится `install-support.py`. Исправленные скрипты должны поставляться вместе с новой сборкой панели: CLI сохраняет конфигурацию с ключом шифрования до создания SQLite.

## Права

| Объект | Владелец | Режим |
|---|---|---|
| `/opt/trusttunnel`, `/opt/trusttunnel/bin`, бинарник endpoint | `root:trusttunnel` | `0750` |
| `/opt/trusttunnel-admin`, `/opt/trusttunnel-admin/bin`, бинарник панели | `root:trusttunnel-admin` | `0750` |
| Скрипт резервного копирования | `root:root` | `0700` |
| `/etc/trusttunnel`, `/run/trusttunnel` | `trusttunnel:trusttunnel` | `0750` |
| `/etc/trusttunnel/tls`, `/var/lib/trusttunnel` | `trusttunnel:trusttunnel` | `0700` |
| `/etc/trusttunnel-admin`, TLS и `/var/lib/trusttunnel-admin` | `trusttunnel-admin:trusttunnel-admin` | `0700` |
| Конфиги, TLS-ключи/цепочки, SQLite и sidecar-файлы | Соответствующая служба | `0600` |
| Управляющий сокет | `trusttunnel:trusttunnel` | `0660`, устанавливает endpoint |
| Unit-файлы, Fail2ban | `root:root` | `0644` |
| Certbot deploy hook | `root:root` | `0750` |
| Состояние установщика `/var/lib/netlane-install` и `state.json` | `root:root` | каталог `0700`, файл `0600` |

Каталоги `/opt/...` и их `bin` задаются явно: права только конечного `bin` не исправляют существующего родителя `0700 root:root`. Служебные пользователи не могут изменять бинарники. `trusttunnel-admin` включён в группу `trusttunnel` для доступа к сокету; приватные ключи VPN остаются `0600` в каталоге `0700` своего пользователя. Общие системные предки `/opt`, `/etc`, `/var/lib` установщик не расширяет: если нестандартные права не допускают выполнение, проверка `runuser ... version` останавливает установку и показывает `namei`.

Ограничения systemd сохранены: `NoNewPrivileges`, `PrivateTmp`, `ProtectHome`, `ProtectSystem=strict`, существующие `ReadWritePaths`, пользователи и capability endpoint `CAP_NET_BIND_SERVICE`. Перед инициализацией реально выполняются оба бинарника от имён служб. Перед запуском проверяется чтение конфигураций/TLS и запись в каталоги данных.

## Административный порт

По умолчанию панель слушает только `127.0.0.1:8443`. В неинтерактивном режиме внешний доступ требует явного `NETLANE_PANEL_ALLOW=203.0.113.7` (через мастер) или `TT_PANEL_ALLOW` (прямой install.sh); для ограниченного доступа нужен активный UFW или `TT_FIREWALL=1`. Публичный доступ всем включается только явным выбором в мастере либо `NETLANE_PANEL_PUBLIC=1` / `TT_PANEL_PUBLIC=1`. Политика применяется до запуска панели.

Для локальной панели можно использовать `ssh -L 8443:127.0.0.1:8443 root@DOMAIN`. Сертификат выписан на DOMAIN: клиентский DNS/hosts должен направлять это имя в локальный туннель; для CLI-проверки подходит `curl --resolve DOMAIN:8443:127.0.0.1 https://DOMAIN:8443/healthz`.

## Возобновление

После сбоя, из того же исправленного комплекта:

```sh
bash setup.sh --resume
```

Для прямого установщика:

```sh
TT_RESUME=1 bash install.sh your.example.com
```

Используйте исходные роль, домен и явно заданную политику доступа. Мастер подхватывает сохранённые домен, роль и политику из root-only состояния. При наличии `config.json` пароль и ключ шифрования не генерируются повторно, база не удаляется. Файлы VPN, credentials и managed state создаются только если отсутствуют. Существующие документы проверяются и не заменяются пустыми шаблонами. Если после прерывания пароль не был показан, он остаётся прежним; восстановление доступа выполняется явной командой `trusttunnel-admin passwd` от root, а не скрытой сменой пароля установщиком.

Установка с завершённым маркером отклоняется, даже с `--resume`: для неё нужен штатный процесс обновления. Работающая установка без маркера не принимается автоматически. Для старой **остановленной** частичной установки допускается явное `--resume` после проверки совпадения домена и роли; конфигурация с публичным listen требует явной политики доступа. Испорченный JSON или база без исходного `config.json` требуют восстановления из резервной копии: без исходного ключа автоматически расшифровать данные нельзя. Установщик ничего не удаляет и не создаёт вместо них новый ключ.

Для ноды перед сетевым join атомарно сохраняется `config.json.pending` с исходным главным сервером. Если токен уже записан, повторный запуск восстанавливает финальный конфиг без повторного расходования приглашения. Подмена главного сервера отклоняется. Старый токен без исходной pending-конфигурации не перезаписывается: требуется исходный конфиг/резервная копия. Если ответ join потерян ещё до сохранения токена, понадобится новое приглашение; восстановить неизвестный секрет невозможно.

Запущенные бинарники не заменяются: если комплект отличается от работающего процесса, возобновление останавливается. Готовность установки фиксируется только после проверки systemd, HTTPS с проверкой сертификата, управляющего сокета, Fail2ban/jail и обоих таймеров. Unit-файлы и hook публикуются атомарно, проверяется совпадение публичных ключей TLS-сертификата и приватного ключа. SSH hardening при ошибке валидации восстанавливается из исходного файла, если он уже существовал.

## Автоматические тесты

Запуск только на локальной машине с Docker Desktop/Linux containers или Docker Engine:

```sh
# Нужны Linux x86_64 бинарники текущей панели и managed endpoint.
python scripts/test-dev-install.py --panel artifacts/trusttunnel-admin --endpoint artifacts/trusttunnel_endpoint
```

Тест строит `ubuntu:24.04` с настоящим systemd и запускает отдельные одноразовые контейнеры. Нет публикации портов, host network, привязки каталогов хоста или host cgroup mounts. Для systemd нужен `--privileged`, namespace cgroup остаётся private. Source bundle передаётся через `docker cp`; контейнеры удаляются после теста.

Проверки: чистая установка через setup.sh, остановка до инициализации при ошибке выполнения бинарника, `SIGKILL` после записи конфигов/БД/служб с последующим --resume, сохранение ключа/пароля/SQLite-сентинела, исправление родителей `root:root 0700`, запрет повторной установки, приватный listen по умолчанию, явный CIDR, сохранение базы без конфигурации. Дополнительно исполняются настоящий Certbot deploy hook и backup unit, проверяются UID процессов и сохранение systemd-hardening. Журналы: `artifacts/installer-tests/`.

Только внешняя выдача ACME заменена локальным доверенным сертификатом. Проверки HTTPS проверяют имя/доверие/срок, не используют `-k`. Это контейнерный тест Ubuntu 24.04 с общим Linux-ядром Docker, не отдельная VPS/VM; публичный challenge Let's Encrypt и DNS провайдера в нём не проверяются. Никакая production-инфраструктура не используется.
